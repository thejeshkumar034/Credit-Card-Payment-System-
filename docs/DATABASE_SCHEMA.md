# Credit Card Payment System — Database Schema

## 1. Database Information

* **Database name:** `credit_card_payment_system`
* **Database engine:** MySQL
* **Character set:** `utf8mb4`
* **Collation:** `utf8mb4_unicode_ci`
* **Schema management:** Django migrations

## 2. Tables

### 2.1 Users — `auth_user`

Django's built-in user table stores authentication and account information.

| Column        | Purpose                |
| ------------- | ---------------------- |
| `id`          | Primary key            |
| `username`    | Unique username        |
| `email`       | User email address     |
| `password`    | Django password hash   |
| `first_name`  | First name             |
| `last_name`   | Last name              |
| `is_staff`    | Admin-site access flag |
| `is_active`   | Account status         |
| `date_joined` | Registration timestamp |

Django's authentication system manages the actual user schema. The columns above are the main fields relevant to this application.

### 2.2 Cards — `cards_card`

Stores saved credit and debit card metadata.

| Column               | Purpose                       |
| -------------------- | ----------------------------- |
| `id`                 | Primary key                   |
| `user_id`            | Foreign key to `auth_user.id` |
| `card_type`          | Credit or debit               |
| `masked_card_number` | Masked card number            |
| `last_four`          | Last four digits              |
| `expiry_month`       | Expiry month                  |
| `expiry_year`        | Expiry year                   |
| `created_at`         | Creation timestamp            |

**Security:** The application does not store the complete card number or CVV.

### 2.3 Transactions — `transactions_transaction`

Stores payment transaction records.

| Column           | Purpose                           |
| ---------------- | --------------------------------- |
| `id`             | Primary key                       |
| `user_id`        | Foreign key to `auth_user.id`     |
| `card_id`        | Foreign key to `cards_card.id`    |
| `amount`         | Payment amount                    |
| `status`         | `PENDING`, `SUCCESS`, or `FAILED` |
| `transaction_id` | Unique transaction identifier     |
| `created_at`     | Creation timestamp                |
| `updated_at`     | Last update timestamp             |

The transaction identifier is generated by the FastAPI payment service. The database's integer `id` is the primary key used by the Django transaction-detail endpoint.

### 2.4 Admin Logs — `audit_logs_adminlog`

Records administrative activities.

| Column          | Purpose                                |
| --------------- | -------------------------------------- |
| `id`            | Primary key                            |
| `admin_user_id` | Optional foreign key to `auth_user.id` |
| `action`        | Activity type                          |
| `description`   | Activity details                       |
| `created_at`    | Activity timestamp                     |

Supported action types include login, export, view, create, update, and delete.

If a user record is deleted, the associated log's user reference can become null while the log record remains.

## 3. Relationships

* One user can have multiple saved cards.
* One user can have multiple transactions.
* One card can be referenced by multiple transactions.
* One user can have multiple admin logs.
* A transaction references both its user and its card.

## 4. Payment Workflow

1. The user authenticates using Django JWT.
2. FastAPI validates the token and identifies the user.
3. FastAPI checks that the selected card belongs to that user.
4. A transaction is inserted with `PENDING` status.
5. The payment simulation changes the status to `SUCCESS` or `FAILED`.
6. Django exposes the transaction through the transaction-history API.

## 5. Data Integrity and Security

* Django ORM and SQLAlchemy ORM are used for database operations.
* User passwords are hashed by Django's authentication system.
* Card ownership is checked before payment processing.
* Full card numbers and CVVs are not stored.
* Transaction identifiers are unique.
* Django migrations manage the application tables.

## 6. Database Backup and Restore

The SQL backup is stored at:

`database/credit_card_payment_system.sql`

To restore a dump that includes the database creation and selection statements:

```bash
mysql -u root -p < database/credit_card_payment_system.sql
```

Run this command from the project root in a terminal where the MySQL client is available.

**Important:** A restore can replace or conflict with existing database objects and data. Test it in a separate development database before restoring over an existing database.
